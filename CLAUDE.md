# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Scrobblr — a music scrobbling service (self-hosted last.fm alternative). This is the **backend** repo: a Rust workspace (Axum + SQLx + PostgreSQL/TimescaleDB + Redis) plus the `@scrobblr/types` package (TypeScript types generated from the Rust models via ts-rs, published to npm). The browser extension and Flutter app live in sibling repos (`scrobblrhq/extension`, `scrobblrhq/mobile`) and consume `@scrobblr/types` from npm.

## Commands

Dev environment is managed with devenv (nix): `devenv up` starts PostgreSQL (with TimescaleDB, DB `scrobblr`) and Redis (password `123`), then runs the migration runner once Postgres is ready. `.env` is loaded automatically (dotenv is enabled in devenv and via `dotenvy` at runtime).

```bash
cargo run -p api          # run the API (requires DATABASE_URL; listens on BIND_ADDR, default 0.0.0.0:8080)
cargo run -p worker       # background jobs (session/now_playing cleanup, metadata enrichment and track lengths, now-playing SSE republish, scrobble classification, ranking weights, coordination detection and precomputed rankings, album attribution, erasing deleted accounts)
cargo run -p worker -- classify report   # classification review CLI (`worker --help` lists commands)
cargo run -p worker -- rank report       # raw vs filtered global rankings (`rank top` prints a stored one as the routes serve it)
cargo run -p worker -- rank cohorts      # coordinated cohorts of the latest detection run (`--dry-run` detects now, `rank detect` stores)
cargo run -p worker -- tracks mb-review  # MusicBrainz matches two other lengths contradict (`--apply` unlinks them)
cargo run -p worker -- albums backfill --dry-run   # what deciding albums by accounts would move (once after 0032; without --dry-run it does)
cargo run -p worker -- uploads gc        # list uploads no row refers to (`--delete` deletes them)
cargo run -p worker -- accounts pending  # accounts waiting to be erased (`accounts erase NAME` erases one now)
cargo run -p worker -- status            # each loop's heartbeat and the queues; exits 1 when one is stalled or failing
just migrate              # apply pending migrations to DATABASE_URL (`just migrate status` lists them)
cargo run -p worker -- import lastfm --user NAME --lastfm USER   # operator import (users import via POST /v1/import/lastfm)

just fmt                  # cargo fmt --all
just lint                 # cargo clippy --workspace --all-targets -- -D warnings
just lint-fix             # clippy --fix
just check                # cargo check --workspace

just test                 # cargo test --workspace; also regenerates TS bindings (see Types pipeline below)
just test-db              # #[ignore]d database tests (need Postgres and Redis; see Migrations)
cargo test -p api <name>  # single test
just sqlx-prepare         # refresh .sqlx/ after a query change (needs a migrated DATABASE_URL)
just openapi              # rewrite openapi.json after an intended API change

just ci                   # CI's first job: fmt-check, lint, test, types-check (stale TS bindings fail)
just ci-db                # CI's database job: migrate DATABASE_URL, test-db, sqlx-check (stale .sqlx/ fails)

just build                # release build of api and worker
backup/test.sh            # backup and restore end to end in a throwaway Compose project (Docker)

# packages/types (bun is the package manager; biome for lint/format)
bun install
cd packages/types && bun run build
```

The justfile exports `SQLX_OFFLINE=true`, so every recipe compiles against the committed `.sqlx/` cache, never the local database's schema (the dev database may lag the migrations). Point `DATABASE_URL` at a scratch database when running `ci-db` or `sqlx-prepare`: `migrate` applies the migrations to it.

CI (`.github/workflows/ci.yml`) runs `just ci`, and `just ci-db` against TimescaleDB 2.29.2 on Postgres 18 and Redis 8 (devenv's versions), on pushes to `main` and pull requests. Its Rust toolchain is pinned to devenv's (`RUST_TOOLCHAIN`), so clippy agrees with local runs: bump it when `devenv.lock` updates Rust.

### SQLx offline mode

Query macros (`sqlx::query!` etc.) compile against the `.sqlx/` cache, so no database is needed to build. Plain `cargo` with `DATABASE_URL` set, as `.env` does, checks them against the live database instead, which must then be migrated; the justfile always forces the cache. When you add or change a query, run `just sqlx-prepare` with `DATABASE_URL` pointing at a migrated database (sqlx-cli is in the devenv shell) and commit the updated `.sqlx/` files; CI's `sqlx-check` fails otherwise.

### Migrations

Numbered plain-SQL files in `migrations/` (`0001_initial.sql` … next free number), applied **in order** by `just migrate` (= `SQLX_OFFLINE=true cargo run -p worker -- migrate`; offline because it must compile before the database has the schema the query macros expect). The runner is `crates/db/src/migrate.rs`: files are embedded at compile time via `sqlx::migrate!` (`crates/db/build.rs` rebuilds on changes), each applied one is recorded with its checksum in `schema_migrations`, and a session advisory lock serializes concurrent runs. Each file runs in one transaction unless its **first line** is `-- no-transaction` (e.g. `0008`, whose `CALL refresh_continuous_aggregate` can't run in one): then each statement runs on its own (retried while it hits `lock_not_available`, e.g. a policy refresh the scheduler just started), so such a file must be safe to re-run. Never edit an applied migration (checksum mismatch) — add a new one. Don't use `sqlx migrate run`: sqlx-cli sends a no-transaction file as one multi-statement query, which Postgres wraps in an implicit transaction.

Migration is a deploy step, never automatic: the API and worker only call `db::migrate::ensure_current` at startup and refuse to run with pending migrations. devenv runs the runner after Postgres starts; docker-compose has a one-shot `migrate` service the API and worker depend on. `just migrate --baseline N` records `1..=N` as applied without running them (for databases migrated by hand before the runner existed). DB tests (`crates/db/tests/`, `#[ignore]`d) each create a throwaway database from `DATABASE_URL`, migrate it through the runner, and drop it.

## Architecture

Rust workspace crates and their dependency direction: `api` → `db` → `shared`; `worker` is a standalone binary.

- **`crates/shared`** — domain models (`models.rs`) and password hashing. Every API-facing model derives `Serialize + JsonSchema + ts_rs::TS`; these three derives keep the OpenAPI spec and the TypeScript types in sync with the Rust structs.
- **`crates/db`** — all SQL lives here as `sqlx` query functions under `src/queries/` (one module per area: auth, users, scrobbles, tracks, charts, feed, enrichment, community, classification, imports, …), plus the migration runner in `src/migrate.rs`. Handlers never write inline SQL (exception: a couple of one-offs in handlers use `sqlx::query_scalar!` directly).
- **`crates/api`** — Axum 0.8 HTTP layer:
  - `router.rs` merges the route groups into one app: authed routes behind `require_auth`, one group per `Access` they need (see Auth model), among them the `write` **upload** group with a larger `DefaultBodyLimit` (8 MiB, for multipart image uploads); public routes; and user routes behind `optional_auth` (injects `AuthUser` if a valid Bearer token is present, without requiring one — needed for things like `is_following` on public profiles and `has_voted` on image candidates). The upload directory is served at `/uploads` (see Uploaded images). Global layers: rate limiting (`RATE_LIMIT_REQUESTS` per `RATE_LIMIT_WINDOW_SECS` per client IP, default 60 a minute, 0 = off; `rate_limit::client_ip`: the peer address, or with `TRUSTED_PROXY_HOPS=N` and a peer in `TRUSTED_PROXIES` (default loopback and private networks) the `X-Forwarded-For` entry the outermost of N proxies appended, so a client reaching the API around its proxies can't name another; the API is served with `ConnectInfo` for this). Every per-address limit counts an IPv6 client by its /64 (`rate_limit::network`), tracing, gzip. CORS (`middleware/cors.rs`): the native API sends none unless `CORS_ALLOWED_ORIGINS` lists origins (or `*`), since the web app calls it from its server and the extension holds host permissions; the protocol routes answer any origin, as Last.fm's and ListenBrainz's APIs do, and `/uploads` sends `Access-Control-Allow-Origin: *`.
  - `middleware/` — `auth.rs` (session/API-token auth and scope checks, inserts `AuthUser`, with the request's `Credential`, into request extensions; handlers extract it with `Extension(auth_user)`), `rate_limit.rs` (the global limit, and `ClientIp` for handlers), `visibility.rs` (enforces `is_private` profiles).
  - `limits.rs` — Redis limits: password-login attempts and the daily scrobble quota (shared by the native and compatible APIs), uploads, follows, exports and deletion requests. Keys carry their window, so a lost `EXPIRE` can't make one permanent.
  - `live.rs` — the `/v1/user/{username}/live` SSE fan-out: one `PSUBSCRIBE now_playing:*` on a Redis connection of its own. **Never subscribe on `AppState::redis`**: a subscribed RESP2 connection refuses every other command, which silently broke rate limiting, logins and now playing for the whole API. Publishing now playing is best-effort. Open streams are capped at 50 per address and 20 per signed-in viewer (the one watching, never the one watched, whose cap anyone could fill), counted in the hub, so per API instance; past them, 429.
  - Redis clients (API and worker) reconnect with backoff and time a command out after 3 s.
  - Logging: `shared::logging::init` for both binaries; `LOG_FORMAT=json` gives one JSON object per line, anything but `text`/`json` stops startup.
  - Panics: release builds unwind. `CatchPanicLayer` answers a panicking handler with the usual opaque 500, the worker's `supervise` restarts a panicked loop (1 s backoff, doubling to 5 min), and `shared::panic::log_panics` sends every panic to the log.
  - `monitoring.rs` — operational routes, outside the OpenAPI spec and behind the rate limit: `/health` (200 `ok`, or 503 naming the database or Redis when it doesn't answer within 2 s), `/health/worker` (503 when a worker loop is stalled or failing, no detail; public, for uptime checks) and `/metrics` (Prometheus text; a 404 unless `METRICS_TOKEN` is set, then 401 without `Bearer` that token). A layer outside every other counts responses by status class and 429s for it. Nothing sensitive goes on the public two.
  - `errors.rs` — `AppError` enum with `IntoResponse` mapping to status codes; all handlers return `ApiResult<T>`. Database/Redis/Internal variants log and return opaque 500s.
  - OpenAPI docs via `aide`: every handler has a sibling `_<name>_doc(TransformOperation)` function registered in the router. Spec served at `/api.json`, Scalar UI at `/docs`. Conventions, all checked by `router/openapi_tests.rs`:
    - Path parameters go through the named structs in `handlers/mod.rs` (`IdPath`, `UuidPath`, `UsernamePath`, …): aide can't name a bare `Path<i64>`, which left the parameter out of the spec.
    - Document errors as `response_with::<4xx, ErrorJson, _>`; `ErrorJson` is the `{ error }` body `AppError` sends. A handler returning `impl IntoApiResponse` must declare its success body (`response::<200, Json<T>>()`), or the spec has none.
    - `router.rs` adds what route groups have in common: bearer security (optional where `optional_auth` runs), 401 and 403 on authenticated groups, 429 everywhere. `compat/docs.rs` describes the protocol routes by hand.
    - `openapi.json` (repo root) is the spec's snapshot: `just test` fails when the spec changes; review the diff, then `just openapi`. Another test fails on an operation without a summary, a success response, its path parameters, or bodies for its successes and errors.

### Auth model

Two credential types, both resolved by the auth middleware:
- **Sessions**: UUID tokens in `user_sessions`, cached in Redis under `session:{id}` (logout must invalidate both; it ends the calling session, or with `?all=true` every one of the user's). A session may do anything. They last 30 days from login; use doesn't extend them.
- **API tokens**: long-lived, stored hashed via `auth_db::hash_api_token`; the raw token is shown only once at creation. Each holds scopes, and none implies another: `scrobble` (`/v1/scrobble`, `/v1/now-playing`), `read` (the account's own data: `GET /v1/user/me`, imports, connected accounts, its community charts and feed) and `write` (changing the account and posting as it: profile, follows, comments, votes, uploads, imports, catalog refreshes). `POST /v1/auth/tokens` defaults to `["scrobble"]` and refuses unknown names and an empty list; a name stored before that check grants nothing.

The middleware never loads the user: both credentials are deleted with it (`ON DELETE CASCADE`), so the session's or token's `user_id` is enough. `last_used_at` (sessions, API tokens, scrobbler credentials) is written at most every 5 minutes, in the background.

**Scopes are enforced per route group.** `router.rs` puts every authenticated route in a group that `require_auth` guards with an `Access`: `Scope(..)`, `Session` or `Any`. A credential without it gets a 403 saying what's missing (`AppError::MissingScope`, `SessionRequired`), which the group also documents in the OpenAPI spec.
- **`Session` routes take no API token**, so a leaked token can't mint a successor, revoke the others, or link an account that keeps scrobbling after its revocation: creating and revoking API tokens, logout, scrobbler credentials (`/v1/scrobbler/*`) and account links; the account as a whole, so it can't carry the account away or delete it: `GET /v1/user/me/export`, `POST /v1/user/me/delete` (see Account export and deletion); and blocks, so it can't show whom the user protects themselves from or lift a block (see Social). `GET /v1/connect/{provider}` starts one with a single-use `state` (Redis, 10 min) mapped to the user; the provider sends the browser to the web app's `/connect/{provider}/callback` (or the API's GET of that path, which forwards it there), whose server finishes with `POST /v1/connect/{provider}/callback` and its session, refused unless the `state` is that user's: otherwise a page could send someone's browser back with its own `state` and link their account to the page owner's.
- **`GET /v1/auth/tokens` is `Any`, but an API token lists only itself.** The browser extension validates a pasted token that way and needs a 200 with a non-empty list. The mobile app's background scrobbler uses its `scrobble` token for scrobbles and now playing only; its UI uses the session, token creation and revocation included. `optional_auth` accepts sessions only.
- **New routes:** `router/tests.rs` (`#[ignore]`d) lists every authenticated route with its access, checks each credential against each, and fails on a route that answers 401 without credentials but isn't listed, or that answers without them but isn't in `PUBLIC`. Its harness, `test_app.rs` (the full router on a throwaway database), is shared with the compat tests.

Third-party scrobblers have their own, `scrobbler_credentials`, which the auth middleware never accepts (see below).

### Metadata enrichment

The worker runs an enrichment pipeline (`crates/worker/src/enrichment/`) over the catalog: MusicBrainz (MBIDs, durations, release dates — 1 req/s hard limit), Cover Art Archive (album covers by MBID), Deezer (artist images + cover fallback; its limiter is shared with the length lookups below), Last.fm (bios, only when `LASTFM_API_KEY` is set). Jobs live in `enrichment_jobs` (queue queries in `db/src/queries/enrichment.rs`), enqueued at ingest for never-enriched entities, by the `POST /v1/{track,artist,album}/{id}/refresh` endpoints, and by periodic backfill/re-sweeps; `done` jobs are deleted a week after they finish (`failed` ones stay, so the backfill doesn't retry them). A track's `mbid_hint` (from imports or what a live client sent; the first one wins, and an enriched track without an mbid is queued again when one arrives) is looked up directly and adopted only if its title and artist match. A recording in `track_mbid_rejections` (migration `0021`, written by `worker tracks mb-review --apply`) is never adopted for that track again, as hint or search result. Merge policy: fill-only-NULL; `mbid` is never overwritten; images/bio are overwritten only on forced refresh; names/titles are never touched; and an image is never touched when `image_locked` is set (a community-voted or user-uploaded image — see below). Provider rate limiters are in-process — run a single worker instance.

The worker also holds an optional Redis client (best-effort — a missing/unreachable `REDIS_URL` only disables this, enrichment still runs): after it fills an artist/album image, it re-publishes `now_playing` over the API's SSE channel for anyone currently playing that entity, so a live now-playing card swaps its fallback for the real cover within seconds instead of showing the pre-enrichment placeholder for the whole track.

### Worker heartbeats

Every loop `supervise` runs gets a `heartbeat::Beat` and reports each run: `ok`, or `failed` with its error (`*_then_wait` when it pauses longer than its interval, as the length lookups back off). Rows live in `worker_heartbeats` (migration `0024`, `db::queries::monitoring`); writes are throttled to one per loop every 30 s unless it starts or stops failing. Each loop's interval is in `heartbeat::LOOPS` (a new loop goes there or `supervise` panics at startup); the worker registers them at startup (rows of loops it no longer runs go), and a loop that isn't configured calls `disable()`. `shared::monitoring` judges them: **stalled** when no run finished within `WORKER_STALL_FACTOR` (default 3) × interval, **failing** when no run succeeded in that time; either makes `worker status` exit 1, `/health/worker` 503 and the worker container unhealthy. Errors from outside services (providers, Spotify, Last.fm) don't fail a loop; database errors do. Queue depths are counted when read, never stored.

### Scrobble classification (anti-botting)

The worker labels every scrobble `counted`, `suspect`, `duplicate` or `no_data` after ingest so rankings can ignore bot plays (`suspect` and `duplicate` are never meant to count). Profiles read the labels (see Profile stats); the ranking weights are made from them (see Global rankings); no cagg changes, and ingest never rejects anything for being suspicious. The pieces: the pure rule in `shared::classification` (offline unit tests), storage and queue in `db::queries::classification` (schema in migrations `0010` and `0012`), and the worker loops plus CLI in `crates/worker/src/classification/`.

- **Lengths:** the rule knows up to three per scrobble: MusicBrainz's `tracks.mb_duration_ms`, the catalog's `tracks.duration_ms` (first client, or Last.fm; Deezer's `deezer_duration_ms` when it has none) and the play's own `scrobbles.duration_ms`. Any can be wrong (MusicBrainz matches snippets, live takes and medleys; crowd-sourced lengths are off), so none is the truth: listening time uses the **longest**, so a wrong short one can't be farmed, and the repeat window the **shortest**, so a wrong long one can't swallow real replays.
- **Duplicates:** a scrobble of the track the user scrobbled less than `min(0.9 × shortest length, 4 min)` before (30 s without a length) is `duplicate`: the same listen reported again by several scrobblers or a retrying one, seconds to ~4 minutes apart in real histories. It uses no budget; copies chain.
- **Rule (listening-time budget):** a scrobble is suspect when the listening time of all scrobbles in the window ending at it, itself included, exceeds `window × max_ratio + slack` (defaults 1 h × 2.0 + 15 min, from `CLASSIFIER_WINDOW_SECS` / `CLASSIFIER_MAX_RATIO` / `CLASSIFIER_SLACK_SECS`; invalid values stop the worker). A scrobble's listening time is the track length, or `scrobbles.listened_ms` when set, clamped between `min(30 s, length/2)` and the length, and capped at one window. When the next scrobble that isn't a duplicate starts before a play could have ended, the play was skipped: from then on it counts the gap, but never less than its scrobble point `min(length/2, 4 min)`. A label therefore depends only on earlier scrobbles. Without any length the scrobble is `no_data`: it uses no budget, so it never counts against anyone.
- **Ceiling:** clients without listened time get at most budget ÷ scrobble point plays counted per window (~67 an hour of 4-minute tracks) and one per repeat window of the same track; clients reporting `listened_ms` can go down to 30 s a play (~270 an hour).
- **Storage is sparse, per user and UTC day:** `scrobble_classification_days` (one row per classified day, with counts and the `classifier_rulesets` id) plus `scrobble_flags` (only non-counted scrobbles, with reason, duration source, occupancy and window load). The `scrobble_labels` view gives one label per scrobble (NULL = not classified yet). Classification only **reads** the `scrobbles` hypertable, so reclassifying compressed history never decompresses chunks. A ruleset is fingerprinted by `RULES_VERSION` and the thresholds: **bump `RULES_VERSION` when the rule's logic changes**, and every stored day becomes stale and is reclassified in the background.
- **Keeping it fresh:** ingest (`ingest_scrobble`, hence also the Spotify poller) queues the scrobble's day with `ON CONFLICT DO NOTHING` and a 30 s settle, so a burst costs one index probe per scrobble. When enrichment first learns a track's MusicBrainz length, it queues the track's plays from the last 30 days. A 5-minute sweep queues days that are missing, classified under another ruleset, or whose count no longer matches `user_activity_daily`. That covers crashed claims and dropped days, but a late insert into an already-materialized bucket reaches it only after the hourly aggregate refresh. The same sweep re-checks `no_data` flags whose track has since gained a length (a new length only ever adds listening time, so it can't clear a suspect). A day whose tail changes queues the next day, whose lookback (one window plus 4 min, for duplicates) it is.
- **Imports:** after inserting history, call `classification::enqueue_scrobble_classification(pool, user_id, from, to)`, alongside `scrobbles::refresh_scrobble_aggregates`.
- **Writes:** a day's write also queues it in `ranking_queue`, and a trigger keeps `user_label_totals` and `users.scrobble_count` in step (Profile stats). Never rewrite labels outside `classify_user_day`.
- **CLI:** `worker classify report [--all] [--user NAME]` shows coverage, totals per ruleset, the users with most suspect and most duplicate scrobbles, clients reporting lengths far below the catalog's or MusicBrainz's, and tracks whose two lengths disagree; with `--user`, that user's worst days. It covers the last 30 days unless given `--from` or `--all`. `reclassify [--user] [--from] [--to] [--dry-run]` recomputes synchronously and prints label transitions; run it with different `CLASSIFIER_*` values plus `--dry-run` to preview a threshold change. `backfill [--dry-run]` queues every missing or stale day.

### Profile stats

A profile shows its user's listening, suspect plays included, never the classifier's duplicates. A trigger on `scrobble_classification_days` (migration `0019`) keeps `users.scrobble_count` = stored scrobbles minus classified duplicates (so every `UserProfile`, search order and Last.fm's `user.getInfo` follow) and `user_label_totals` (per user: classified, counted, suspect, duplicate, no_data), whatever writes the days. `GET /v1/user/{username}` and `/v1/user/me` add `scrobble_breakdown` (`users_db::scrobble_breakdown`): `verified` + `unverified` (`suspect + no_data + pending`) = `scrobble_count`. Top artists/tracks subtract duplicates from `scrobble_flags` and add `unverified_count`; the heatmap subtracts the day's duplicates; recent scrobbles (native and `user.getRecentTracks`) leave them out and carry a `status`. Not-yet-classified plays count as plays until labelled.

### Global rankings (anti-botting)

Guide: `docs/rankings.md`. Each scrobble gets a weight from 0 to 1 for global rankings, never for profiles: the pure function in `shared::ranking` (offline unit tests), storage, queue and ranking queries in `db::queries::rankings` (migration `0018`), the worker loops and `worker rank` CLI in `crates/worker/src/rankings/`, the public routes in `crates/api/src/handlers/rankings.rs` (see Public rankings).

- **Weight** = label (`counted` 1, `suspect`/`duplicate` 0, `no_data` 0.5, unclassified 0) × import (0, and nothing else applies to imports) × account (0 before the account is 7 days old; `users.created_at` can't be backdated) × listened time (0 under the scrobble point of the shortest plausible length, 1 s tolerance; 0.25 without `listened_ms`) × client (verified and known 1, unknown 0.5). Then per user and UTC day only the first 4 weighted plays of a track and 30 of an artist keep their weight (caps count plays, not weight). Settings: `RANKING_*` (invalid values stop the worker); the ruleset is fingerprinted by `WEIGHTS_VERSION` and the params: **bump `WEIGHTS_VERSION` when the logic changes**, and every day is reweighed.
- **Listened time and our clients:** the extension and the mobile app scrobble at `max(30 s, min(their reported length / 2, 4 min))` (4 min when the app has no length), so the point is measured on the length the client reported unless it is under half of MusicBrainz's or the catalog's. Changing the clients' thresholds means checking `listen_point_ms`.
- **Rankings** (`rankings`): per period, listeners first (a user's credit is their weight for the entity over `listener_weight()`, one known-client play without listened time, at most 1), then weighted plays; raw counts every user and scrobble. Read from `ranking_daily` (user, day, track: plays and weight), never raw scrobbles, which compression segments by user. Only days from `retained_from(today)` on (the year period plus a week) keep rows: the sweep purges older ones daily, `weigh_user_day` removes instead of writing them, and `enqueue_stale` skips them.
- **Snapshots** (migration `0022`): a ranking over `ranking_daily` takes seconds, so the worker's `run_snapshots` loop keeps each `Period` (week, month, year: rolling UTC days ending today) precomputed: `refresh_snapshots` replaces the period's `ranking_snapshots` rows (artist and track) and their top 1,000 `ranking_entries` (filtered order with the coordination factors applied, entities with weight only, raw counts beside) in one transaction, so readers see the old snapshot until it commits and keep it if it fails (retried after 5 min). Due when missing, older than 1 h (week, month) or 1 day (year), from another UTC day, another ruleset or another coordination run (`coordination_run_id`), or `invalidated` by an account erase (migration `0027`). `computed_at`, `to_day` and `pending_days` (user-days still queued then) say how fresh it is; `Period::stale_after` says when it is late (15 min past due). `served_page` is what the routes read, `snapshot_entries` what `rank top` prints.
- **Keeping it fresh:** `classify_user_day` queues the day in `ranking_queue` in its transaction; the worker weighs queued days (`weigh_user_day`, under the classification's per-day advisory lock, reading scrobbles by user only) and a 5-minute sweep queues days missing, weighed with other params, from an older classification (`classified_at`), or whose classification is gone.
- **CLI:** `worker rank report [--from|--all] [--to] [--limit]` (coverage, plays per reason, top N artists/tracks by listeners and by plays, raw beside filtered, users by plays vs weight); `recompute [--user] [--from] [--to] [--dry-run]`; `backfill`; `refresh [--period]` (recompute snapshots now); `top [--period] [--kind] [--limit]` (print a stored one). Preview other settings with `recompute` on a scratch copy. `scripts/synthetic/` builds a population and four botting attacks in a scratch database (docs/rankings.md). Bulk inserts into `scrobbles` must skip the per-row counter trigger some other way than `ALTER TABLE scrobbles DISABLE TRIGGER`, which doesn't reach TimescaleDB's chunks (the scripts use `session_replication_role = replica`, or rows marked as an import, which the trigger skips); with the trigger on, one transaction rewriting a user's row thousands of times crawls.

### Public rankings

`GET /v1/rankings/artists` and `/v1/rankings/tracks` (docs/rankings.md, Public routes): public routes (no credential, `PUBLIC` in `router/tests.rs`) serving the stored snapshots without computing anything. `?period=week|month|year` (default week, else 400), `limit` (50, clamped to 1–200), `offset` (negative 400, past the end an empty page). The body (`ArtistRanking`/`TrackRanking`, `shared::models`) carries `from`/`to`/`computed_at`/`stale`/`total` and entries shaped like `TopArtist`/`TopTrack` with whole `listeners` (the order) and `plays` (weighted); never raw counts, fractions, users, factors or cohorts.

- **One statement per page** (`rankings::served_page`): the page and its snapshot's version come from the same snapshot while a refresh commits.
- **Small groups:** entries credited with fewer than `RANKING_MIN_LISTENERS` (5, read by the API and by `rank top`) listeners aren't served (`shared::ranking::is_served`); a credit is one at most, so that's 5 accounts, and ordered by listeners the cut is a prefix. Private profiles count like any other, unnamed, as in every catalog aggregate.
- **Freshness:** no snapshot yet is a 404 (cacheable 60 s); a late one is served with `stale: true`, never hidden.
- **Caching:** `Cache-Control: public, max-age=300, stale-while-revalidate=300` and a weak ETag of `computed_at`, the minimum and staleness; `If-None-Match` gets a 304 after one primary-key lookup. A new field that changes for the same snapshot must go into the ETag.

### Catalog counts

Catalog-wide counts add up every user's plays, private profiles' included, so they follow the rankings' minimum (migration `0026`, docs/privacy.md): `Track.scrobble_count` and `Artist.scrobble_count` (`GET /v1/track/{id}`, `/v1/artist/{id}`, `/v1/search`) are `null` unless `RANKING_MIN_LISTENERS` distinct users played the entity, and an artist's top tracks leave such tracks out (of its 200 most played). `Album.scrobble_count` (`GET /v1/album/{id}`) is its tracks' plays, under the same minimum (`album_has_listeners`, migration `0029`, samples each track's listeners). `Artist.listener_count` was never kept and is always `null`. The test is `track_has_listeners`/`artist_has_listeners` (SQL functions): a skip scan over `(entity, user)` indexes on the daily aggregates, a few index probes however popular the entity. It reads the materializations through `track_listener_rows`/`artist_listener_rows`, plain views the migration made of them, because the aggregates' own views (a union with unmaterialized rows, grouped again) can't give an index scan ordered by user across chunks: a listener counts from the next refresh. Queries serving a `Track` or `Artist` to clients go through `tracks_db::public_track`/`public_artist`/`search_*`; the lookups (`find_*`, `find_or_create_*`) return no counts at all, so no path serves a raw one. The listener sections (`/v1/{artist,track}/{id}/listeners`) name public profiles with their own play counts, as their profiles do.

### Account export and deletion

docs/privacy.md is what an operator reads. Both routes take a session (`router/tests.rs`).

- **Export** (`GET /v1/user/me/export`, `handlers/account.rs`, `crates/api/src/export/`): a ZIP streamed as it is read, never stored (nothing to expire or forget): `README.txt`, `account.json` (`export::FORMAT`; secrets never selected, nor who blocks or removed the user; `export::NOT_INCLUDED` says what is left out and why), `scrobbles.csv` and `scrobbles.json` (two keyset-paged passes, 5,000 a statement, oldest first, each page its own statement so no long transaction holds chunk locks the compression policy wants; labels, never weights), `uploads/`. `export/zip.rs` writes the archive front to back (deflated entries with data descriptors, ZIP64 when needed; tested against the `zip` crate). 3 a day per account, 10 per address (`limits::export_attempt`, fails closed), 2 at once per API instance (503 past it). The response is `application/zip`, which the compression layer skips. A failure mid-stream can only cut the archive short (logged).
- **Deletion request** (`POST /v1/user/me/delete` with `password` and `confirm` = the username): 5 attempts an hour per account, 10 per address (`limits::deletion_attempt`, fails closed); a wrong password is a 403 (`AppError::WrongPassword`), not a 401. `accounts::schedule_deletion` sets `users.delete_after` (migration `0027`) (now + `ACCOUNT_DELETION_GRACE_DAYS`, 7, 0–30) and in the same transaction deletes sessions (their Redis entries after), API tokens, scrobbler credentials and approved authorizations, connected accounts, now playing, and cancels imports. History stays during the grace period.
- **Pending accounts are hidden**: `User.delete_after` (never serialized) makes `ensure_profile_visible` a 404, follow targets and the Last.fm API's `user` not found; search, listener lists, followers/following, community charts, the feed, comments and image candidates filter `delete_after IS NULL`. Their plays still count in aggregates and rankings until the erase. The row holds the username and email until then.
- **Restore:** only the native `/v1/auth/login` (`account_restored: true`) restores, through `accounts::restore`, refused once `erase_started_at` is set; the scrobbler APIs' password logins refuse a pending account, so a player logging in again on its own never undoes a deletion.
- **Erase** (`accounts::erase`, worker loop `account erasure` every minute, `worker accounts erase NAME` now): claims a due account (`erase_started_at`), deletes its scrobbles one chunk per transaction (`show_chunks`, named directly), taking them off the track/artist/album counters in the same transaction (after the delete, ids sorted, deadlocks retried), then its rows in the aggregates' materializations directly, then labels, weights and coordination days in batches, then queues, likes (taken off candidates' `vote_count`), and the user row, which every other reference follows by cascade; marks `ranking_snapshots.invalidated` when it had weights; returns its upload keys no row refers to any more (avatar of kind `avatars`, candidates; promoted artwork stays) for the worker to delete through `shared::storage`. Every step is safe to repeat; a claim older than 15 minutes (a failed erase) is taken again.
- **Aggregates without a refresh:** a delete from `scrobbles` invalidates the aggregates' buckets over its range, and the refresh recomputes them for everyone (measured: 10 min for three years of 4.8M rows). Every aggregate here is grouped by user, so the user's rows in the materializations are exactly their share: chunk deletes run with `timescaledb.skip_cagg_invalidation = on` and those rows are deleted instead, while a guard transaction holds the materializations in `SHARE ROW EXCLUSIVE` (refreshes wait, reads don't) from before the first delete until they are clean, so no refresh writes them back from rows not yet deleted. TimescaleDB's direct batch delete on compressed chunks logs invalidations whatever the setting (2.29.2 and 2.30.2 alike), so the erase turns it off (`enable_compressed_direct_batch_delete = off`, and no limit on decompressed tuples): the user's segments are decompressed and their rows deleted, leaving the chunks partially compressed for the compression policy's segmentwise recompression (~20 ms a chunk). A new aggregate without `user_id` makes the erase fall back to ordinary invalidating deletes (`aggregates_by_refresh`). Measured on a 503,700-scrobble account (1.3M rows, 157 chunks, 2.29/pg18): 124 s, 0 invalidations, other users' p99 335 ms during it (111 ms without); 201,480 scrobbles on 2.30/pg16: 58 s, 0 invalidations.
- **Tests:** `crates/db/tests/accounts.rs` erases a user with a row in every table, then checks, generically, every `bigint` `user_id`/`…_user_id` column and every foreign key to `users` (tables, views, aggregates) for rows about them, every text column for their name, that every foreign key to `users` cascades, that counters and aggregates equal a recount, and that no invalidation was logged. A new table holding a user id fails it unless the erase covers it.
- **Usernames:** held while the account is pending, free again once it is erased (no trace of it is kept).

### Coordination detection (cross-account anti-botting)

Guide: `docs/rankings.md` (Coordination). What the per-play weights can't see: accounts older than 7 days, each a plausible fan, pushing the same entities. Pure detection in `shared::coordination` (offline unit tests), registration-address hashing in `shared::origin`, storage in `db::queries::coordination` (migration `0025`), the loop in `crates/worker/src/rankings/coordination.rs`. It never blocks, deletes or relabels anything: its output is a factor from 0 to 1 per (user, day) in `coordination_days` (rows below 1 only) that `rankings()` and snapshot refreshes multiply listener credits and weights by. Profiles never read it.

- **Groups, not pairs:** every artist and track with at least `MIN_COHORT` accounts weighing for it in the window (28 days of `ranking_daily`) is a group; signals compare a group's members with the active population. Linear in (account, entity) pairs plus sorting the sync window's plays (14 days of scrobbles, read once). No account is compared with every other.
- **Primary signals** (each gated by an excess of 10 accounts and z ≥ 4 against the population's expectation, each member getting its cell's purity, the share of the cell the excess explains): `age` (registered in the same 7-day window, up to 4 windows), `origin` (same registration address or network hash, values held by 3+ members), `client` (the client family a member scrobbled the entity with, one used by under 2 % of the other accounts), `sync` (crowds of 3+ other accounts within ±2 min of a play, 10× what the hour around it explains, on 4+ of 14 days). **Behavioural** (can't act alone): `shape` (share of weight on the account's top 3 artists), `burst` (new to the entity in a group mostly new to it).
- **Suspicion** = Σ weight × evidence, capped at 1 (primary 0.5, client 0.35, behavioural 0.125 each), an account's being its highest over its groups; factor = 1 up to 0.4, 0 from 0.9, smoothstep between. One primary at full strength leaves ~0.90; two at 0.8 purity ~0.10. **Bump `COORDINATION_VERSION` when the logic changes.** `RANKING_COORDINATION_*` (invalid values stop the worker); `RANKING_COORDINATION=off|report|apply` (report lists cohorts and stores no factor).
- **Factors in rankings:** a user's factor for the period is their days' factors weighed by their weight on each day (`ranking_days`), joined by hash (`SET LOCAL enable_mergejoin = off`: the planner otherwise sorts a million per-user rows to disk); it multiplies listener credits after they are capped (a farm account with lots of weight would otherwise stay a full listener at any factor) and weights. A run rewrites its window's days and leaves earlier days as the last run covering them left them, so the year keeps a stopped farm dented; they expire with the weights. `rankings()` returns the uncoordinated listeners/weight/rank beside.
- **Runs:** every 6 hours, when the UTC day or the params change, under advisory lock `coordination` (snapshot refreshes take it shared), CPU on `spawn_blocking`; a failed run keeps the previous factors (retried in 10 min). Below `MIN_ACCOUNTS` (200) active accounts nothing is judged. Cohorts = flagged accounts by the group of their strongest primary evidence; `coordination_runs`/`_cohorts`/`_accounts` keep 30 days for review.
- **Registration origins** (`registration_origins`): `register` records `shared::origin` hashes (64-bit HMAC-SHA256 of the address, IPv6 by /64, and of the network, IPv4 /24 or IPv6 /48) of the address limits use (`ClientIp`, so spoofed `X-Forwarded-For` can't poison it) when `REGISTRATION_HASH_KEY` is set; never the address. The key lives outside the database (with it the IPv4 space can be brute-forced); values carry `key_id`, so another key's never match. The worker deletes rows older than `REGISTRATION_ORIGIN_DAYS` (90).
- **CLI:** `worker rank detect [--dry-run]`, `worker rank cohorts [--dry-run] [--limit] [--members]`; `rank report` adds a with/without-coordination section. `scripts/synthetic/coordination.sql` (+ `coordination-results.sql`) builds four farms and three honest crowds (docs/rankings.md).

### Last.fm history import

How users bring their Last.fm history over: `POST /v1/import/lastfm` (API) or `worker import lastfm --user NAME --lastfm USER` (operator CLI). The pieces: the client and cursor in `shared::lastfm`, dedup in `shared::import`, jobs and the page transaction in `db::queries::imports` (migration `0011`), the runner and CLI in `crates/worker/src/lastfm_import/`, and track lengths in `crates/worker/src/enrichment/lengths.rs`.

- **Jobs** (`scrobble_imports`): at most one active per user. A worker leases a job for 25 pages at a time, so imports take turns, and every page commits together with the job's cursor. A crash, restart or expired lease therefore resumes at the next page. The walk goes newest to oldest under a window fixed when the job starts. It runs in segments of 20 pages, each restarting at page 1 one second above the oldest scrobble seen; that avoids deep page offsets and is correct whether Last.fm's `to` is inclusive or not.
- **Errors:** 29 (rate limit) cools every Last.fm caller down for 60 s without spending an attempt. Other transient errors back off from 30 s to 1 h, and the job fails after 10 attempts. 6 fails it as `user_not_found` and 17 as `history_hidden` (a verified import signs requests with the user's session, which can read a hidden history). `LASTFM_IMPORT_MAX_SCROBBLES` fails it as `cap_reached`.
- **Writes** (`record_page`, one transaction per page):
  - Catalog upserts are set-based and use ingest's normalization; new tracks get their primary credit.
  - Dedup (`shared::import::new_plays`) compares against the user's stored rows in the page's time span. It skips an earlier import's row with the same second and track, and a live scrobble of the same track within 10 min, matched one-for-one.
  - Rows are inserted with `source = 'lastfm_import'` and `import_id`. `import_id` is set by the server, so rules should trust it rather than `source`.
  - Counters are updated set-based: `increment_scrobble_counts` skips rows with `import_id`, and `last_seen_at` only moves forward.
  - Old history lands in the uncompressed part of compressed chunks, or in new uncompressed chunks; when the job ends (done or failed) the importer runs the compression policy at once (`scrobbles::compress_history`) rather than leaving them, and their bloated indexes, for up to 12 h. The primary-key uniqueness check decompresses overlapping batches in memory, so insert cost grows with the number of users active in that week.
- **Checkpoints** (segment boundary, end of a lease's pages, end of the job; tracked as `pending_from`/`pending_to`) — never per scrobble:
  - `refresh_scrobble_aggregates`, retried while the scheduled refresh holds the lock;
  - `enqueue_scrobble_classification`;
  - enrichment for new catalog entries at priority 20–29 by play count, below live ingest.
- **Re-imports** start 14 days before the last completed import's `window_to`, since Last.fm accepts scrobbles up to two weeks late. `full` rescans everything. Neither duplicates anything.
- **Track lengths:** Last.fm history has none, which would leave the classifier with only `no_data`.
  - A backfill asks `track.getInfo` (2/s inside the shared 4/s Last.fm limiter) about tracks with no length anywhere, most scrobbled first. It fills the catalog `duration_ms` and doesn't ask again for 30 days after a miss.
  - The MusicBrainz track job looks up the recording mbid Last.fm reported (`tracks.mbid_hint`) directly, adopting it only if its title and artist match.
  - Deezer's public search (no key, `enrichment::lengths::DeezerLengths`, 1/s inside the Deezer limiter enrichment shares) is asked about tracks with no length, then about tracks whose catalog and MusicBrainz lengths differ by 1.5x or more. Track search ignores `artist:` filters, so it searches plain words and accepts a hit only if the artist (or the first artist we credit) and the title match, " - Note" and "(Note)" alike, version notes included; hits of 30 s or less are previews or snippets and ignored. The length goes to `deezer_duration_ms` (migration `0020`), never into `duration_ms`, so it stays an independent witness; the classifier and the weights read `COALESCE(duration_ms, deezer_duration_ms)` as the catalog length. Misses are asked again after 30 days.
  - The classifier's sweep relabels `no_data` days as lengths arrive.
- **Anti-abuse:**
  - API imports require connecting the Last.fm account through its web auth (`GET /v1/connect/lastfm`). That needs `LASTFM_SHARED_SECRET` and `TOKEN_ENCRYPTION_KEY`, and `connected_accounts` allows one Scrobblr user per Last.fm account. These imports are `verified`.
  - API imports are limited to one a day per user and are capped.
  - Every imported day goes through classification, and the ranking weights give imported plays `RANKING_IMPORT_WEIGHT` (0): they count on the user's profile, never in global rankings.
  - CLI imports are trusted as coming from an operator and are stored with `verified = false`.
- **Tests:** the worker's tests run imports against an in-process fake Last.fm (`crates/worker/src/fake_lastfm.rs`), never the real API.

### Uploaded images

Operator guide: `docs/uploads.md`. The database stores an upload's **key**, never its URL; image columns (`users.image_url`, `artists.image_url`, `albums.image_url`, `image_candidates.url`) also hold absolute URLs from enrichment providers or users, kept as they are.

- **Keys** (`shared::media::UploadKey`): `{avatars,artists,albums}/{2 hex}/{32 hex}.jpg`, random and never reused, so a stored file never changes. `UploadKey::parse` is the only way from a stored value to a path and refuses anything that could leave the root. Keys from before migration `0017` are `{uuid}.jpg` and have no kind.
- **URLs**: models serialize a key as `{UPLOAD_PUBLIC_URL}/{key}` (`#[serde(serialize_with = "crate::media::serialize_opt_url")]` on every image field, checked by a test in `models.rs`; a new image field needs it too) and leave other values alone. The base is process-wide (`shared::media::set_public_url`), set at startup by the API and the worker, whose now-playing republish carries images; `UPLOAD_PUBLIC_URL` defaults to `{PUBLIC_BASE_URL}/uploads`. Code writing image URLs by hand calls `shared::media::public_url` (the Last.fm-compatible `images()`). `PUBLIC_BASE_URL` itself is `AppState::public_base_url`, for links the API builds to itself.
- **Processing** (`api::media::image`): format sniffed from the bytes (JPEG, PNG, WebP only), refused over 12000 px a side, 40 megapixels or 256 MiB of decoder allocation before the bitmap exists, EXIF orientation applied, fitted within 512 px (avatars) or 1024 px (artwork), alpha flattened onto white, re-encoded as JPEG, so no metadata survives. At most two decodes run at once. Decoders must reject malformed files, never panic (a panic is a 500; tested with truncated and corrupted files). Bodies over `MAX_UPLOAD_BYTES` (8 MiB) are 413s. Uploads are limited to 20 an hour per account and 30 per address, refused ones included (`limits::upload_attempt`, behind `require_auth`; fails open).
- **Storage** (`api::media`, over `shared::storage`, which the worker uses to delete an erased account's files): handlers call `Media::store`/`read`/`delete`, never the filesystem. `Storage` is an enum with one backend, `LocalStorage` (`UPLOAD_DIR`): writes go to `.tmp/` (0700) and are renamed into place; files are 0644 and directories 0755 whatever the umask, so a static server running as another user can read them. An S3-compatible bucket would be another variant; neither handlers nor stored data change. Deletion is best-effort: failures are logged, never returned; `worker uploads gc` (`crates/worker/src/uploads.rs`) finds what was left: files under `UPLOAD_DIR` whose key no image column holds (`db::queries::uploads::referenced_keys`), older than 24 h so an upload not yet in the database is never taken, deleted only with `--delete`.
- **Serving**: the API serves the root at `/uploads` (keys only: no `.tmp/`, no directories) with a one-year immutable `Cache-Control` and `nosniff`; `UPLOAD_PUBLIC_URL` can point at a static server or CDN instead.

### Community contributions (uploads, image voting, comments)

`crates/api/src/handlers/uploads.rs` + `community.rs`, backed by `db/src/queries/community.rs`. Uploads are multipart (`image` field), stored as described under Uploaded images.

- **Avatars** (`POST /v1/user/me/avatar`) replace the user's own `image_url` directly. A replaced or removed avatar (by an upload or `PATCH /v1/user/me`) is deleted; `update_profile` locks the row and returns the image it replaced. Only keys of kind `avatars` are deleted: `PATCH` stores https URLs only (http ones from before stay until replaced), so an avatar key in a user's row was uploaded by that user, while a kindless key may have been converted by `0017` from a URL the user typed. `PATCH` refuses URLs of our own uploads; the current avatar's URL, whatever it is, leaves it as it is: the mobile app's profile form sends back the URL it was given. An upload whose database write fails is deleted again.
- **Artist/album art** is last.fm-style community voting, **add-only**: an upload creates a row in `image_candidates` (uploader auto-likes their own). Likes go through `image_candidate_votes`; the most-liked candidate becomes the entity's displayed image once it reaches `MIN_VOTES_TO_DEFAULT` (3), which sets `image_url` + `image_locked`. Promotion only — a withdrawn like never demotes the shown image.
- **Comments** (`comments` table) attach to artists or tracks; reads are public, writes authed, deletes owner-only.

Listener/social sections and the private-profile rules: `artist_listeners`/`track_listeners`/`search_users` and follow lists all exclude `is_private` users (follow lists but to the account itself), so a private account stays undiscoverable in aggregate surfaces. Its profile and everything under it 403 to everyone but its owner (`middleware/visibility.rs`), followers included: following takes no approval, so a follower is anyone who asked. They, comments and image candidates also leave out accounts waiting to be erased.

### Social: follows, charts and the feed

Guide: `docs/social.md` (routes, examples, numbers). One visibility rule everywhere: an account is visible to a viewer when it isn't waiting to be erased and is public or the viewer's own; a private profile is its owner's alone, followers included (following takes no approval).

- **Follows** (`handlers/users.rs`, `users_db::follow_page`): `/v1/user/{username}/followers` and `/following` page newest follow first by a keyset `Cursor` (`shared::cursor`, migration `0028`), with `is_following`/`follows_you` for a signed-in viewer; profiles carry `followers_count`/`following_count` (every follow, private ones included), `follows_you` and `blocking`; `/friends` returns the 100 most recent of each. `MAX_FOLLOWING` (2,000, 409 past it, serialized per follower by an advisory lock), `limits::follow_attempt` (100 an hour per account, 300 per address, fails open; unfollowing is free) and `limits::pair_attempt` (3 new follows of one account a day).
- **Blocks** (`handlers/blocks.rs`, `db::queries::blocks`, migration `0031`, session only): a block ends the follows both ways and refuses new ones; the blocked account, signed in, finds the blocker missing (`ensure_profile_visible` answers 404, as `blocks_db::relation` says `blocked_by`), and every list of people leaves out, for a signed-in viewer, accounts blocking it or blocked by it (follow lists, search, listeners, comments, image candidates, feed, community charts: the `NOT EXISTS (… user_blocks …)` filter, which a new list naming people needs too). A block also closes the blocked account's live streams of the blocker (`live::close_for`). Removed followers (`follower_removals`) can't follow again for 30 days. Follows, blocks and removals take the pair's advisory lock (`blocks::lock_pair`). 10,000 blocks, 200 actions an hour per account and 600 per address, 3 blocks of one account a day. Nobody is told who blocks them; the export lists blocks made, never received.
- **Charts of a user** (`handlers/charts.rs`, `db::queries::charts`): `/v1/user/{username}/charts/{artists,tracks,albums}`, periods `7d|30d|90d|12m|all` or `from`/`to` (UTC days, 366 at most; `shared::charts::resolve`), `limit` 50/200, `offset`. The profile's plays from the daily aggregates and flags (duplicates out, suspect and `no_data` in `unverified_count`); an album's plays are its tracks' (`tracks.album_id`, see Album attribution). A page is cut before its names are looked up. Weak ETag of the user's breakdown and the hour; each page kept 15 min in Redis under it (`chart:v1:*`). `top-artists`/`top-tracks` read the same queries.
- **Community charts** (`/v1/user/me/community/{artists,tracks,albums}`, `read`): the visible followed accounts' `ranking_daily` weights and coordination factors, ranked as `rankings()` does, entries under `RANKING_MIN_LISTENERS` credits left out, no `all` (weights expire). At most `COMMUNITY_USER_DAYS` (14,600) account-days: the most recently active accounts first, all 2,000 over a week, 40 over a year; cost ~20 ms a thousand. The transaction forces a custom plan (a generic one was 3× slower). The ranking is kept 5 min in Redis keyed by a hash of the account ids (`community:v1:*`), so follow and privacy changes need no invalidation.
- **Feed** (`/v1/user/me/feed`, `read`, `db::queries::feed`): 14 days of the visible followed accounts' scrobbles, newest first, without suspect plays and duplicates, keyset pages by (`played_at`, `id`). A page reads growing windows (1 h, ×4) for the accounts whose `last_seen_at` reaches the window, which therefore must be the latest play: the counter trigger keeps the greater since migration `0030`.

### Album attribution

Guide: `docs/social.md` (Albums). `tracks.album_id` is the one album a track's plays count for, everywhere (charts, community charts, `Album.scrobble_count`, `album_has_listeners`); it used to be the first album a scrobble named. Pure rule in `shared::albums` (offline unit tests), votes and queue in `db::queries::albums` (migration `0032`), the worker loop and `worker albums backfill` in `crates/worker/src/albums.rs`.

- **Votes** (`track_album_votes`, one per account and track): the album its plays named, the latest when it changes (`albums_db::record_vote` after `ingest_scrobble`'s commit, read before written; `record_votes` per import page). A changed vote queues the track (`album_attribution_queue`, 30 s settle).
- **Weight**: one per account at least `RANKING_MIN_ACCOUNT_DAYS` old and not waiting to be erased, times its lowest coordination factor of the coordination window; ×2 for a release MusicBrainz lists the recording on (`tracks.mb_release_titles`, lowercased titles from the recording's last lookup, kept only for the track's own mbid). A new album needs 1.5× the current one's score and one account more.
- **Queued** on a vote change, at an account's coming of age (`recheck_at`), at deletion request, restore and erase (`enqueue_voted`), when release titles change and at `tracks mb-review --apply`. Coordination runs queue nothing.
- **Don't** store the album in `ranking_daily` or any aggregate: a move would have to rewrite them. The community album chart joins `tracks` once per (account, day, track) row (measured: 1.1–1.3× the tracks chart; a stored column, 8 bytes a row plus a `track_id` index, reached 0.7×).
- `worker albums backfill [--dry-run]`: votes of every stored scrobble, a chunk a statement, into a temp table, then every track decided; once after migrating to `0032`.

### Track credits (multiple artists)

`tracks.artist_id` remains the **primary** artist: it backs `UNIQUE (artist_id, title_normalized)` and the denormalized `scrobbles.artist_id` every aggregate query reads. `track_artists` (migration `0007`) holds the full credit list, one row per artist with a `track_artist_role` of `primary` or `featured` plus a billing `position`; a partial unique index keeps at most one `primary` per track, and the `primary` row always mirrors `tracks.artist_id`. Chosen over a `BIGINT[]` column because Postgres can't foreign-key array elements.

Every live source (`ingest_scrobble`, both now-playing paths and the Spotify poller, which maps `track.artists[0]` to primary and the rest to featured) goes through `tracks_db::resolve`: artist, album, track, credits, the client's MusicBrainz hint and the enrichment enqueue. Its `find_or_create_*` read before inserting, so a known catalog entry costs no write (an upsert that rewrote it was three flushed commits per scrobble). Credits are **add-only** — a client omitting a collaborator never erases one. Aggregate surfaces (`artist_top_tracks`, `artist_listeners`, search) deliberately stay primary-artist-only; making featured credits count there means rewriting them to join `track_artists`. The artist and track sections sum the daily aggregates (covering indexes from migration `0015`), never raw scrobbles: compressed chunks are segmented by user, so a query by artist or track would decompress all history.

### Native scrobbling limits

`POST /v1/scrobble` refuses plays more than 30 days old (422; history comes in through imports, and the mobile app queues plays offline with no age cap, hence more than the compatible APIs' 14 days) and takes from the same daily quota as the compatible APIs (`SCROBBLER_DAILY_LIMIT`, 429 past it; duplicates and rejected plays give theirs back). Client track lengths outside 1 ms–24 h count as unknown, `source` is cut to 100 characters, and `recording_mbid` (optional) becomes the track's `mbid_hint`.

### Scrobble clients

`scrobbles.source` is whatever the client claims. `scrobbles.client_id` (migration `0013`) points at `scrobble_clients`: the protocol the scrobble arrived by, the client as that protocol identifies it, and `verified` when the server checked that identity. Native `/v1/scrobble` records `scrobblr` with its claimed source (unverified), the Spotify poller `spotify` (verified), the compatibility APIs `lastfm` (the api_key), `audioscrobbler` (client id and version) and `listenbrainz` (`submission_client` or `media_player`). Ingest callers pass `ScrobbleInput.client_id`; the API resolves ids through `AppState.clients`, a bounded cache, since names are client-chosen. Imports leave it NULL (`import_id` already says where they came from).

### Scrobbler-compatible APIs (Last.fm, Audioscrobbler 1.2, ListenBrainz)

Existing scrobblers work by changing only the server URL (user guide: `docs/scrobbler-clients.md`). Code in `crates/api/src/compat/`: `mod.rs` (config from `SCROBBLER_*`/`WEB_APP_URL`, the router, and the shared submit path and limits), `lastfm.rs` (`/2.0/`), `audioscrobbler.rs` (`/` and `/1.2/` with `hs=true`, `/1.2/nowplaying`, `/1.2/submissions`), `listenbrainz.rs` (`/1/submit-listens`, `/1/validate-token`), `credentials.rs` (`/api/auth/` and the web app's `/v1/scrobbler/*`); storage in `db::queries::scrobblers` (migration `0014`). The protocol routes are a plain axum `Router` merged before the rate-limit layer.

- **Credentials** (`scrobbler_credentials`, sha256-hashed): `token`s users create (`POST /v1/scrobbler/tokens`) and paste into clients as a ListenBrainz token, an Audioscrobbler password or a Last.fm password; `session`s, Last.fm session keys from `auth.getMobileSession` with the account password or `auth.getSession` after browser approval, bound to the api_key they were issued to. A token given as the Last.fm password comes back as the session key itself, so revoking it signs the client out. They reach only these endpoints, never the native API; managing them takes a session, never an API token.
- **Signatures:** clients sign with secrets of Last.fm's or of their developer, public in practice, so a signature authenticates nothing; the credential does. A signature is checked when the server knows the secret (`SCROBBLER_API_KEYS`, or the api_key itself, which GNU FM clients such as Pano Scrobbler sign with): a wrong one is error 13. Unknown keys pass as unverified unless `SCROBBLER_STRICT_API_KEYS`. `scrobble_clients.verified` records which.
- **Password logins** (`auth.getMobileSession`, the 1.2 handshake, and the native `/v1/auth/login`, sharing `limits.rs`): attempts are counted before checking, 20 per IP and 10 per IP and username per 15 min (Redis, fails closed; nothing per username alone, which would let anyone lock an account), and `handlers::auth::verify_password_login`, shared with `/v1/auth/login`, keeps a missing account as slow as a wrong password. Account passwords only with `SCROBBLER_PASSWORD_LOGIN`, which defaults to off when `AUTH_APP_KEYS` gates the native login (an unsigned login here would get around it). 1.2's handshake proves knowledge of md5(password), so it takes tokens holding a legacy secret (their md5, encrypted with `TOKEN_ENCRYPTION_KEY`); its auth tokens are burned on use and must be within 5 min of the server clock; its sessions live in Redis (24 h, sliding) and are checked against the credential on every request.
- **Same pipeline:** `compat::submit` sends every play through `ingest_scrobble` (validation, dedup, catalog, credits, enrichment, classification) with `source` = the protocol and the client's `client_id`. Before that: plays older than 14 days or more than 5 min ahead are ignored, a per-user daily quota (`SCROBBLER_DAILY_LIMIT`, default 3000, shared with native scrobbles, Redis, fails open) and 120 requests a minute per user apply, and batches are capped (50 for Last.fm and 1.2, 1000 for a ListenBrainz import). A duplicate counts as accepted, so retries are idempotent. MusicBrainz recording ids clients send (`mbid`, 1.2's `m`, ListenBrainz's `additional_info.recording_mbid`) become enrichment hints.
- **Browser flow:** `/api/auth/?api_key=…&token=…` (desktop) or `?api_key=…&cb=…` (web) redirects to `{WEB_APP_URL}/scrobbler/authorize` with the same query. The page uses `GET /v1/scrobbler/authorizations/{token}` and `POST …/{token}/approve`, or `POST /v1/scrobbler/authorizations {api_key, callback}` for the web flow, then sends the browser to the returned callback.
- **Tests:** `compat/tests.rs` (`#[ignore]`d, Postgres and Redis) replays the requests of Pano Scrobbler, Web Scrobbler, mpris-scrobbler and Audioscrobbler 1.2 clients, signatures included.

### Auth input rules and client attestation

`shared::validation` owns every credential rule (username charset/length, RFC-lite email structure, password length + complexity, display-name sanitization) and is enforced **only at registration** (and the display-name rule on `PATCH /v1/user/me`) — `login` applies just the bounds needed to keep a hostile body away from Argon2, since re-applying the current rules would lock out older accounts. `login` also verifies against a decoy hash when no user matches, so response latency can't be used to enumerate usernames.

`middleware/app_signature.rs` gates `/v1/auth/register` and `/v1/auth/login` behind an HMAC-SHA256 request signature when `AUTH_APP_KEYS` is set (unset = open, so existing clients keep working). Nonces are burned in Redis, and a Redis failure rejects rather than passes.

With `REGISTRATION_HASH_KEY` set, `register` also records keyed hashes of where the account registered from (see Coordination detection); a failed write is logged, never fails the registration.

### Username semantics

Lookups (`find_by_username`, `find_by_email`) are case-insensitive (`lower(col) = lower($1)`, indexed by migration `0016`), but the DB UNIQUE constraint on `users.username` is case-sensitive — keep the two in mind when touching registration/lookup code. `RESERVED_USERNAMES` in `handlers/auth.rs` blocks names that collide with route literals like `/user/me`, checked case-insensitively.

### Clients (sibling repos)

The web app (SvelteKit, its own repo and deployment) is a server-side proxy: its server calls the API with the user's session as bearer and the user's address as the only `X-Forwarded-For` entry. `openapi.json` is its contract. The API sends browsers to pages under `WEB_APP_URL`: `/scrobbler/authorize` (compat browser approval), `/connect/{provider}/callback` (account links) and `/user/{username}` (Last.fm-compatible profile links); renaming one breaks those flows.

`scrobblrhq/extension` (Plasmo) pastes an API token, calls `/v1/now-playing` and `/v1/scrobble` without retrying, and validates the token with `GET /v1/auth/tokens`. `scrobblrhq/mobile` (Flutter): the UI uses the session; the background scrobbler a provisioned `scrobble` token, with an offline queue (500 plays, no age cap) that drops a play on any 4xx except 429. Its Dart models in `lib/api/models.dart` mirror the API **by hand** — update them when API-facing models change (`ProfileResponse.scrobble_breakdown`, `TopArtist`/`TopTrack.unverified_count`, `ScrobbleRich.status` are the latest; `ArtistRanking`/`TrackRanking`, `Track`/`Artist.scrobble_count` and `Artist.listener_count` becoming nullable, `AuthResponse.account_restored`, the export and deletion routes, and the social routes (`FollowPage`, profile counts and `follows_you`, `Album`, the chart, community and feed models), and blocks (`BlockPage`, `BlockEntry`, `ProfileResponse.blocking`) are not mirrored yet).

### Docker

`docker-compose.yml` is the production setup (one host, managed by hand: `git pull`, `up -d --build`; docs/operations.md covers start/update/backup/restore, monitoring and what a reverse proxy in front must do). It runs `db`, `redis`, the one-shot `migrate`, `api`, `worker` (which mounts the uploads volume to delete erased accounts' files) and `backup`, and no proxy: the API is published on `${API_BIND:-127.0.0.1}:${API_PORT:-8080}`. It passes optional settings as `${VAR:-}`, an empty string when unset, so every reader must treat a blank value as unset (`non_empty_env` in the worker, the same filter elsewhere). The image build sees no `*.md`, no `scripts/` and no `backup/` (`.dockerignore`): don't `include_str!` one. Every service's log rotates (10 MB × 5).

Backups (`backup/`): the `backup` service is built on the database's image (`x-db-image`, so `pg_dump` matches the server and its TimescaleDB) plus rclone, and runs `backup/scrobblr-backup.sh` (busybox ash; `shellcheck` it): daily at `BACKUP_TIME` into `BACKUP_DIR`, catch-up and hourly retries, a backup verified in `.partial-NAME` before it gets its name, restic-style retention, an optional `BACKUP_REMOTE` copy and `BACKUP_PING_URL`. It only reads the app's data (read-only uploads mount, `pg_dump`'s read-only transaction). The `restore` service (profile `restore`) recreates the database at the manifest's TimescaleDB version between `timescaledb_pre_restore()`/`_post_restore()`. `backup/test.sh` exercises both, failures included, against a throwaway project; run it after changing either.

### Types pipeline (Rust → TypeScript)

`#[ts(export)]` on shared models + `TS_RS_EXPORT_DIR = packages/types/src/generated` (set in `.cargo/config.toml`) means **running `cargo test` regenerates the TS bindings** in `packages/types`, published to npm as `@scrobblr/types` (`.github/workflows/types-release.yml`) for the extension and the web app. If you change a shared model, run `cargo test -p shared` and commit the regenerated files (`just types-check` fails otherwise). ts-rs covers `crates/shared`'s models only, not the request and response types handlers define; `openapi.json` covers both and is meant to replace the package once its consumers move (keep the package working until then).
